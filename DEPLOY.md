# Hosting askDB MCP on Render

This deploys the **Streamable HTTP** transport ([src/http.js](src/http.js)) as a Render web service, so clients that cannot spawn a local process — ChatGPT connectors, Claude Code on someone else's laptop — can reach it over HTTPS. The stdio entry point is not involved.

The payoff: your Pinecone key lives in one place instead of on everyone's machine, and each person gets a URL plus a token rather than a repo to clone.

```
Claude Code / ChatGPT ──HTTPS + Bearer──► Render (askdb-mcp) ──► Pinecone
```

---

## 1. Push the repo

Render deploys from GitHub, GitLab or Bitbucket. `render.yaml` and `.node-version` need to be on the branch you deploy.

```bash
git add render.yaml .node-version DEPLOY.md
git commit -m "chore: render blueprint"
git push
```

`.gitignore` already excludes `.env`, so no key is committed. Worth confirming with `git status` before pushing.

## 2. Create the service

Dashboard → **New** → **Blueprint** → pick the repo → Render reads [render.yaml](render.yaml) and shows one web service, `askdb-mcp`.

It prompts for the one value marked `sync: false`:

| Variable | Where it comes from |
| --- | --- |
| `PINECONE_API_KEY` | [app.pinecone.io](https://app.pinecone.io) → API Keys, for the project owning the `ask-db` index |

`MCP_AUTH_TOKEN` is generated by Render — you don't invent it. Click **Apply**.

The first build runs `npm ci --omit=dev` then `npm run start:http`. Watch the logs for:

```
[askdb-mcp] http ready on http://0.0.0.0:10000/mcp · index=ask-db · auth=bearer
```

`auth=bearer` is the line that matters. If it says `auth=NONE`, the token variable didn't take and the endpoint is open — fix it before sharing the URL.

## 3. Grab the URL and token

- **URL** — top of the service page, e.g. `https://askdb-mcp.onrender.com`. The MCP endpoint is that plus `/mcp`.
- **Token** — service → **Environment** → `MCP_AUTH_TOKEN` → reveal.

Verify from your machine:

```bash
curl https://askdb-mcp.onrender.com/health
# {"status":"ok","index":"ask-db","uptimeSeconds":8}

curl -s -o /dev/null -w '%{http_code}\n' -X POST https://askdb-mcp.onrender.com/mcp \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
# 401  ← correct: no token
```

A `200` on that second call means the endpoint is unauthenticated. Stop and fix `MCP_AUTH_TOKEN`.

Then with the token:

```bash
curl -X POST https://askdb-mcp.onrender.com/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

You should get `search_schema`, `get_table_schema` and `list_tables` back. The `Accept` header is required — Streamable HTTP rejects requests that don't accept both content types.

## 4. Connect clients

**Claude Code** (CLI, desktop and IDE extensions share this config):

```bash
claude mcp add --transport http askdb https://askdb-mcp.onrender.com/mcp \
  --scope user \
  --header "Authorization: Bearer <token>"
```

Check with `claude mcp list` → `askdb: ... ✓ Connected`.

**ChatGPT** — Settings → Connectors → Developer mode → add the same URL with an `Authorization: Bearer <token>` header.

**Cursor / Claude Desktop** — MCP settings, HTTP transport, same URL and header.

This is Route A in [SETUP.md](SETUP.md) — that's the page to send teammates.

## Things that will bite you

**The free plan sleeps.** After 15 minutes idle the instance spins down, and the next request takes ~30–60s to wake it. MCP clients connect at startup with a much shorter timeout, so a cold service shows up as "failed to connect" and works fine on the second try. See [Keeping it awake](#keeping-it-awake).

**Rotating the token.** Change `MCP_AUTH_TOKEN` in the Environment tab; Render redeploys and every existing client breaks until re-added with the new value. There's one shared token, not per-user ones — the app compares against a single string. If you need per-person revocation, put an API gateway in front, or run one service per team.

**The URL is your whole schema.** Anyone holding URL + token can read every table definition in the index. It's DDL, not data — askDB never connects to your database — but treat it as internal.

**Region latency.** The blueprint uses `oregon`. If your Pinecone index and your users are in Asia, switch `region: singapore` — but note Render will not move an existing service between regions, so it has to be set before the first deploy or the service recreated.

**`npm ci` needs the lockfile in sync.** If `package.json` and `package-lock.json` disagree, the build fails outright rather than resolving it. Run `npm install` and commit the updated lockfile after any dependency change.

## Keeping it awake

`GET /health` is the wake-up endpoint. It needs no token, returns no secrets, and — because Render wakes an instance on *any* inbound request — hitting it is what brings a sleeping service back:

```bash
curl https://askdb-mcp.onrender.com/health
# {"status":"ok","index":"ask-db","uptimeSeconds":412}
```

`uptimeSeconds` is the field to watch. Ping twice a few minutes apart:

- **uptime grows** → same process, the service stayed warm.
- **uptime back near zero** → it slept and your ping cold-started it. Keep-alive isn't working.

Three ways to keep it warm, best first:

1. **Pay for it.** `plan: starter` in [render.yaml](render.yaml) — instances never sleep. Everything below is working around the free tier.
2. **GitHub Actions** — [.github/workflows/keep-alive.yml](.github/workflows/keep-alive.yml) pings every 10 minutes, already in this repo. Set one repository *variable* to switch it on: Settings → Secrets and variables → Actions → Variables → `RENDER_HEALTH_URL` = `https://<your-service>.onrender.com/health`. It also has a **Run workflow** button for waking the service by hand.
3. **An external uptime monitor** (UptimeRobot, cron-job.org, Better Stack) pointed at the same URL on a 10-minute interval.

Two caveats on the Actions route, both real:

- GitHub delays scheduled workflows when its runners are busy — often past the 15-minute idle window. It reduces cold starts; it doesn't eliminate them.
- Scheduled workflows are **disabled automatically after 60 days with no commits** to the repo. If cold starts quietly return months from now, check that first.

Don't ping more often than every 10 minutes. It buys nothing, and on the free plan it burns the instance-hours you're trying to preserve.

## Changing configuration later

Editing `render.yaml` and pushing updates the service on the next sync. Values entered in the dashboard (`sync: false` ones, and anything you override by hand) win over the blueprint, so if a change to `render.yaml` seems to do nothing, check whether that key was set manually in the Environment tab.

Full variable reference is in [README.md](README.md#configuration).

## Deploying elsewhere

Nothing here is Render-specific beyond the blueprint file. Any host works if it:

- runs `npm run start:http`,
- sets `HTTP_HOST=0.0.0.0` and lets the app read `PORT` from the environment,
- terminates TLS in front, and
- sets `MCP_AUTH_TOKEN`.

The transport is stateless — a fresh server per request — so it scales horizontally with no sticky sessions.
